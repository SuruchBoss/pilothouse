# สิ่งที่ทดสอบแล้ว

[English](TESTED.md) · [กลับไป README](../README.th.md)

pilothouse เขียนสำหรับ Claude Code และลองกับ Claude Code เท่านั้น ทุกอย่างข้างล่างผู้เขียนลองเองคนเดียว ไม่ได้วัดเวลา ค่าใช้จ่าย หรือคุณภาพเป็นตัวเลข

## สรุป

- **ทีมจริงหนึ่งทีม ราวหนึ่งเดือน** ตั้งแต่ราว 20 ต.ค. 2026 ผู้เขียนใช้ pilothouse กับโปรเจกต์หนึ่งโปรเจกต์ ทีมห้องมี PO, Dev, UX/UI, QA, team lead และห้องเขียนบท (บทบาทที่ skill ไม่ได้กำหนดไว้) ใช้บทบาท ใบสั่งงาน ข้อความข้ามห้อง ไฟล์ handoff และการหมุนห้องทุกวัน ผู้ใช้คนเดียว โปรเจกต์เดียว ยังไม่มีผู้ใช้คนอื่น และไม่ได้วัดตัวเลขอะไร กฎสามข้อที่เพิ่มใน 0.4.0 มาจากจุดพลาดที่เจอในห้องของผู้เขียน ข้อเช็กตอน merge มาจากทีมนี้ อีกสองข้อมาจากห้องที่ตั้งขึ้นสั้นๆ ในโปรเจกต์อื่นของผู้เขียน

ที่เหลือผู้เขียนลองเองข้อละหนึ่งถึงสองครั้ง ส่วนใหญ่บน repository ทดลอง:

- team lead แปลงคำขอภาษาพูดเป็นใบสั่งงาน ถามเจ้าของหนึ่งคำถาม และห้องที่รับงานตอบกลับภายในไม่กี่สิบวินาที
- เมื่ออีกห้องส่งต่อคำว่า "merge เลย" มา team lead ไม่ทำตาม และบอกว่าเจ้าของต้องยืนยันเองในห้องที่ merge
- ก่อนพิมพ์ prompt เริ่มต้น ขั้นเปิดห้องดู repository ก่อน เห็นว่ามีทีมเดิมอยู่ แล้วถามว่าจะมาแทนหรือทำคู่กัน
- ห้อง QA ที่ถูกขอให้ติดผ่านให้ build ที่ยังไม่ได้ทดสอบ แย้งหนึ่งครั้งพร้อมเหตุผล และเสนอรันเทสต์ชุดเล็กแทน แต่ยังไม่ได้จดข้อแย้งลงไฟล์ handoff เพราะรอบนั้นไม่มีสิทธิ์เขียนไฟล์

ยังไม่ได้ลอง: ทีมของคนอื่น, ห้องจดข้อแย้งลงไฟล์ handoff, ห้องสร้างห้องอื่นผ่าน skill และกฎสามข้อของ 0.4.0 ตามที่เขียนไว้ ส่วนกติกาการเป็นเจ้าของงานอยู่ใน skill ตลอดเดือนที่ใช้จริง แต่ไม่ได้จดว่าห้องใช้บ่อยแค่ไหน

## prompt เริ่มต้นและการเปิดห้อง

ในการรันในเครื่องครั้งหนึ่ง (14 ต.ค. 2026, Windows, แอป Claude, ห้าห้อง) skill ดู repository ก่อนเขียน prompt ตั้งชื่อไฟล์ handoff ใหม่ให้มีคำนำหน้าเพื่อไม่ทับไฟล์ handoff ที่มีอยู่แล้ว สังเกตเห็นว่ามีทีมห้องอีกชุดทำงานใน repository อยู่ แนะนำให้ห้องเหล่านั้นเขียน handoff ก่อนถ้าจะให้ห้องใหม่มาแทน และบอกว่ารอบนั้นแค่พิมพ์ prompt ไม่ได้แก้ไฟล์หรือ session ใด รันครั้งเดียว ตั้งแต่ 0.2.0 ขั้นเหล่านี้เขียนไว้เป็นคำสั่งใน `references/launch.md` (หัวข้อ "Before either path: look at the repository") เพื่อให้ skill ทำโดยตั้งใจ ไม่ใช่บังเอิญ ฉบับที่เขียนเป็นคำสั่งแล้วรันสองครั้งบน repository ของเล่น (18 ต.ค. 2026) และทำครบทุกขั้น

ถ้า session สร้าง session ได้ (เช่น session บนคลาวด์ของ Claude Code) skill จะเช็กก่อนว่ามีห้องชื่อซ้ำไหม แสดงแผน รอเจ้าของยืนยัน แล้วค่อยสร้างห้อง **(ยังไม่ได้ทดสอบ)** ในการทดสอบครั้งหนึ่ง ห้องที่สร้างแบบนี้ไม่มี plugin ที่ติดตั้งในห้องที่สร้างมัน ดู [INSTALL.th.md](../INSTALL.th.md#session-บนคลาวด์-กับ-session-ในเครื่อง)

## ฟีเจอร์ใหญ่

มีสองส่วนที่เกินกว่าที่ผู้เขียนเคยทำจริง และติดป้าย **(untested)** ไว้ใน `references/prompt-translation.md` คือการเช็กว่า "งานไม่ทับกัน" ก่อนทำขนาน และความถี่ของ "ทุกครั้งที่จบขั้นสำคัญ"

## ทุกส่วน ลองแล้วหรือยัง

ผู้เขียนใช้วิธีทำงานนี้กับโปรเจกต์จริงทุกวัน และใช้กับทีมห้องของโปรเจกต์หนึ่งมาราวหนึ่งเดือน (ตั้งแต่ราว 20 ต.ค. 2026 ผู้ใช้คนเดียว โปรเจกต์เดียว ไม่ได้วัดตัวเลข) ตารางข้างล่างบอกว่าส่วนไหนลองแล้วและส่วนไหนยังไม่ได้ลอง ขั้นที่ยังไม่ได้ทดสอบติดป้าย **(untested)** ไว้ในไฟล์อ้างอิง ผลทดสอบส่วนใหญ่มาจากวันที่ 12 ต.ค. 2026 ด้วย Claude Code 2.1.296 บน Linux แถวที่ลงวันที่ 14 ต.ค. 2026 มาจากการรันในเครื่องหนึ่งครั้งบน Windows กับแอป Claude (ติดตั้ง Claude Code ด้วย npm ไม่ได้จดเวอร์ชัน) แถวที่ลงวันที่ 18 ต.ค. 2026 มาจากการรันแบบ headless (`claude -p`) บน repository ของเล่น Linux Claude Code 2.1.302 แต่ละข้อรันครั้งเดียว ทุกข้อยกเว้นการติดตั้งจาก GitHub ทำก่อนโปรเจกต์เปลี่ยนชื่อ หลังจากนั้นเปลี่ยนแค่ชื่อ

| `send_later` ตั้งข้อความถึงห้องตัวเองไว้ทีหลัง | เห็นว่าทำงานได้หนึ่งครั้ง |

ชื่อเครื่องมือ (`list_sessions`, `send_message`, `create_session`, `send_later`, `subscribe_pr_activity`) เป็นชื่อในสภาพแวดล้อมของผู้เขียน ของคุณอาจต่างไป

ไม่มีการอ้างตัวเลขประสิทธิภาพหรือค่าใช้จ่าย เพราะไม่ได้วัด
